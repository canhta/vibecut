# xtask

Workspace checks, native-media provisioning and development build admission. This binary is tooling, outside the product dependency graph.

Run from a checkout with `cargo xtask <command>`. The Cargo alias builds the launcher in `target/xtask`, independently of the checkout's product target. Product compilation on shared macOS and Windows developer machines uses `cargo xtask build -- <command...>`. The wrapper applies `ffmpeg::environment`, so every admitted command finds and loads the provisioned LGPL SDK at build and run time. Hosted CI runners run Cargo directly. Nested xtask commands keep the same native runpath flags and library paths, so direct and aggregate checks share Cargo fingerprints.

| Command | Behaviour |
|---|---|
| `build -- COMMAND [ARGS...]` | FIFO admission and command exit status on macOS and Windows; OS-native arguments, inherited standard streams |
| `prune [--make-room] [--dry-run]` | Remove verified targets whose checkout is gone and prune above-capacity idle targets; `--make-room` explicitly evicts at most one oldest idle verified target to admit another; `--dry-run` prints the plan |
| `build-cap --json` | Host checkout-target capacity, current directory count, disk budget and candidates in pruning order, for dispatchers |
| `checks`, `docs`, `i18n`, `layers`, `assets` | Repository policy; one forbidden-name scan covers tracked files and branch commit messages before `docs`, which includes the docs index, README module maps, tracker-free Markdown, relative links and anchors that resolve, and no reference-checkout source paths, against only-shrinking `xtask/docs-baseline.txt`; `i18n` rejects the first catalog key that breaks ascending order inside its `// <area>` section; `checks` also checks formatting and the integration-test entry point |
| `modules` | Module structure gate: no `mod.rs`, responsibility docs, banned names (tests included), folder width, intra-crate layer direction from `xtask/modules.toml` (crate and `[[crate.folder]]` tables), and one sorted `support::control` import per line in the control catalog test, with only-shrinking `xtask/modules-baseline.txt` |
| `catalog` | Regenerate `crates/engine/catalog.digest` and `docs/product/agent-control/commands.md` from the registry (the engine `control_catalog` example); declarations must be in ascending command-id order, and the example names the first out-of-order id before writing |
| `clippy`, `test`, `lint`, `ci [--require-oracles]` | Individual or aggregate [verification](../docs/engineering/verification.md); `ci` refuses in a linked worktree unless `CI` is set |
| `ffmpeg [--target PLATFORM]`, `ffmpeg --cache-key` | Resolve/provision native media dependencies and cache identity |
| `media-bench`, `clip-eval SET [OPTIONS]` | Media and labelled clip-pipeline measurements |
| `new-crate NAME` | Scaffold a core library already admitted in the architecture table |

## Build slots

The per-user cache is `.cache/vibecut` beneath `HOME` (`USERPROFILE` on Windows). Each checkout has `target/wt-<first 32 hex digits of SHA-256 of its canonical absolute root>`, independent of admission slot number. The short name stays within Windows native build path limits; an existing target with a different or unreadable owner is refused. Workspace outputs, incremental sessions and Cargo fingerprints survive builds in other checkouts; admission never touches source timestamps or removes workspace artifacts. Cargo alone detects edits within that checkout. A per-checkout OS lock serializes commands using the same target before they enter the admission queue; it follows the same descendant lifetime as the slot lock.

OS-locked slots are concurrency leases. `locks/build-queue` holds numbered, locked waiter files; `locks/admission` serializes enqueue, stale-entry cleanup, slot claims and target-capacity publication. No process IDs establish liveness: crashed waiters release their locks automatically and the next waiter removes dead queue files. Admission is FIFO and prefers the checkout's previous free lease, then the lowest number. Shrinking capacity never releases or kills a running build; leases above a smaller count remain counted in the CPU budget.

The slot ceiling is computed when the wrapper starts and enforced at each admission: `min(logical CPUs, floor(total_memory * 0.70 / 3 GiB) + 1, 64)`. 3 GiB is the peak reserve each running slot holds after compile; the extra slot is the first build, which is never memory-gated. `VIBECUT_BUILD_SLOTS=1..=logical CPUs` (capped at 64) overrides the ceiling; zero, out-of-range, non-numeric or non-UTF-8 values are rejected with a typed error before queueing.

Default Cargo jobs share a budget of twice the logical CPUs. Under the admission lock each command reserves `min(max(2, logical CPUs / (live leases + 1)), remaining jobs)`: a lone build takes every CPU, the second takes half the host, and each later one less, while the ceiling only bounds leases. Fewer than two remaining jobs holds admission, and a held build waits in the FIFO queue instead of starting slow. Reservations cover all live slot leases, including those above a reduced ceiling, stay fixed until the lease releases, and never resize or kill existing children. Each slot's `locks/slot-N.jobs` records its job count or an `exclusive` marker; only a held lease makes the record live. Missing or invalid metadata for a live lease reserves the whole budget and holds admission until the lease exits. All wrappers must implement this protocol, so drain older binaries and rebuild launchers before relying on the budget.

An explicit `CARGO_BUILD_JOBS` or command argument `--jobs`, `--jobs=N`, `-j N` or `-jN` (recognized anywhere in the wrapped arguments, including nested xtask commands) is honoured even above the host budget. Such a command reserves the entire budget and waits until all other leases release; no default-jobs command overlaps it.

Only the first active build bypasses the resource gates. Every extra slot requires all of:
- a 20-second ramp since the last admission;
- free physical memory, minus a 3 GiB peak reserve for every running slot, at or above 30%;
- load below the bound: 1-minute loadavg below twice the logical CPUs on Unix, aggregate processor load below 90% on Windows (two `GetSystemTimes` samples).

A neighbour admitted during compile keeps the whole reserve until its lease ends, because link and test fan-out happen late. A build admitted while instant free memory is already below 30% halves its own `CARGO_BUILD_JOBS` (never below one). Probe failure blocks extra admission. macOS uses `sysctl kern.memorystatus_level` and `hw.memsize`; Linux reads `MemAvailable`/`MemTotal` from `/proc/meminfo` and the first field of `/proc/loadavg` (a missing, zero-total, truncated or unparsable source holds the slot); Windows uses `GlobalMemoryStatusEx` with `GetSystemTimes`. Other Unix systems admit by available slots within the CPU-derived ceiling.

On Unix the wrapped command inherits only its slot descriptor; queue and admission descriptors keep close-on-exec. The launcher restores close-on-exec on its own slot descriptor right after spawning, then waits. The slot lock releases on the last descriptor close, so killing the launcher, or a descendant outliving its command, cannot free the target directory early. A command that closes inherited descriptors must finish its protected work first. On Windows the launcher puts itself in a kill-on-close Job Object (`win-custody`) before taking any lock, so the command and every descendant join it at creation. Killing the launcher, even with `taskkill /F` and no `/T`, makes the kernel kill the whole tree, and a descendant left by a normally exiting command dies when the launcher exits. The launcher holds the slot lock until its process ends. Standard streams stay inherited on both platforms.

Checkout-target capacity is `floor((free disk + bytes already in checkout targets - 30 GiB) / local warm reserve)`. The cache volume supplies free bytes; Windows uses logical file sizes and Unix uses allocated blocks. Counting allocated targets back into the budget keeps capacity stable as they fill. The first-run reserve is the existing 40 GiB per-target policy budget. Versioned `build-reserve.json` in the per-user cache records a qualified warm measurement and the observed target high-water; missing, malformed, oversized or unknown-version state returns to the bootstrap. Only a successful exact `cargo test --workspace` or `cargo xtask ci [--require-oracles]` with nonempty output qualifies a smaller warm sample. Crate-only, incomplete and failed runs cannot lower it; any observed growth raises the high-water, including growth in a live or failed build. Learned samples require a matching compiler, host target, workspace manifests, Cargo configuration and target/profile environment. Explicit target/profile/features and unknown command configurations use the bootstrap unless matched. No calibration workspace build is needed to start using the wrapper.

`cargo xtask build-cap --json` exposes the same local calculation as admission and pruning for the default workspace-test configuration. It reports `capacity`, `directories`, effective `warm_bytes`, `bootstrap_bytes`, `reserve_source`, `qualified_warm_bytes`, `observed_peak_bytes`, a configuration hash, volume `free_bytes`, `floor_bytes` and `targets` (directory, checkout, bytes, `removed`, `owner_valid`, `in_use`) in pruning order. A new target above capacity, or any build below the 30 GiB free-space floor, is refused with idle pruning candidates. Existing targets remain reusable at capacity. `cargo xtask prune` removes verified removed-checkout targets first, then oldest verified idle targets only while above capacity. Ordinary cleanup preserves valid warm targets at exact capacity. `cargo xtask prune --make-room` removes verified removed-checkout targets, then at most one oldest verified idle target when still at capacity; below capacity it leaves warm targets alone. Both `prune --make-room --dry-run` and `prune --dry-run --make-room` preview that same plan. Held or unverified-owner targets are always preserved; use ordinary cleanup first if more than one target must be retired to reach the cap. A live checkout stays warm while within capacity. Idle targets drop stale incremental sessions; above 40 GiB they shed dependencies oldest first, then are removed if still oversized. Old `target/slot-N` directories are also age/size-pruned under their original slot locks, so running launchers retain their files. Disk query failures refuse a build. The same reserve contract runs on every platform; disk probes and accounting remain platform-specific.

New targets build from scratch; build-script output embeds absolute target paths, so copying a dependency seed's run receipts would be incorrect. The wrapper keeps incremental compilation for each checkout.

Child builds receive their reserved Cargo jobs and clear `RUSTC_WRAPPER`. No external compiler cache is required; per-checkout targets retain incremental compilation.

Successful exact `cargo xtask ci [--require-oracles]` commands leave receipts in `ci-receipts`, keyed by Git tree and oracle mode. Only trees clean before waiting, after admission and after execution qualify, including untracked files. An identical clean tree reuses its receipt across rebases. Receipts are local evidence and do not replace environment-specific release checks.

Windows `ci` and `test` link and run ai's standalone `whisper` and `gipformer` library tests before the default-feature workspace suite; both commands run that one suite, so the platform coverage does not depend on which aggregate invoked it.

## FFmpeg

`ffmpeg` resolves and builds the latest stable FFmpeg from verified source, logs the version and admits only the target matching the running host. Every platform builds static zlib from its release archive and enables FFmpeg's PNG codec. The recipe pins the published SHA-256 per zlib version, so a newly resolved release is refused until the pin is reviewed and updated; a corrupt or substituted archive is removed before any install prefix exists.

Linux builds the GPL FFmpeg with libx264 and admits only `linux-x86_64`/`linux-aarch64`. It needs Bash, Make, Perl, pkg-config, Clang/LLVM (`clang`, `clang++`, `llvm-ar`, `llvm-nm`), CMake, Ninja, NASM on x86_64, and the app's desktop dependencies: `libasound2-dev`, `libxkbcommon-dev`, `libwayland-dev`, `libudev-dev`, `libx11-dev`, `libxcursor-dev`, `libxrandr-dev`, `libxi-dev`, `libxinerama-dev`, `libgl1-mesa-dev` and `libegl1-mesa-dev`. Managed tools carry an `$ORIGIN/../lib` rpath, and Cargo children receive `FFMPEG_DIR`, `PKG_CONFIG_PATH` and `LD_LIBRARY_PATH`.

Offscreen desktop rendering tests also require a Vulkan loader and a software adapter
on Linux (`libvulkan1` and `mesa-vulkan-drivers` on Ubuntu). The test harness prefers
software rendering and fails when no adapter is available; Mesa llvmpipe receipts
prove offscreen rendering only, not physical GPU acceptance. The Linux CI setup
installs these prerequisites even when native-media caches hit.

Windows needs architecture-matched MSYS2 CLANG64 (x64) or CLANGARM64 (arm64), Bash, Make, Perl (libvpx configure), CMake, Ninja, pkg-config, NASM and Clang/LLVM; Rust uses MSVC. Native xtask caches under `USERPROFILE`, resolves Bash/Make/cygpath to absolute MSYS2 `usr/bin` paths on `PATH` and logs them. Incomplete installations are refused; Windows/WSL/Git Bash are never substituted. Static Opus/libvpx builds request static pkg-config metadata, including private pthread links.

Windows excludes FFmpeg's `gfxcapture` screen filter through configuration; case-insensitive builds resolve libc++'s `<version>` to the archive's `VERSION`. For workspace checks xtask merges general, underscore-target and hyphen-target `BINDGEN_EXTRA_CLANG_ARGS` in that order, then appends AMX include guards and an explicit native MSVC Clang target in the hyphen-target variable. The target applies to FFmpeg and Whisper because MSYS2 libclang's GNU default has unsigned enums that disagree with whisper-rs's MSVC representation. The AMX headers are excluded together until upstream bindings handle vector layouts. Workspace Cargo children receive MSVC/SDK header paths in `INCLUDE`, discovered through `cc`'s Windows registry support or inherited from a configured developer shell; only `INCLUDE` is forwarded from that environment, to preserve the FFmpeg DLL search path. Missing MSVC tools or SDK paths fail with setup guidance.

Windows workspace Cargo children also receive the managed static `/MD` Sherpa library directory through `SHERPA_ONNX_LIB_DIR`. Native AI archive selection, cache integrity and overrides belong to [ai's native build contract](../crates/ai/src/gipformer/README.md).

On Windows the FFmpeg environment owner projects only DLLs from the verified native prefix into `runtime-dlls` using atomic hard links, and prepends that directory to child `PATH`. It excludes the prefix's `bin` from inherited `PATH` so managed programs cannot shadow the external test oracles. Existing runtime links must match the native DLL hashes.

External `ffmpeg` and `ffprobe` are separately installed tools for oracle admission ([verification](../docs/engineering/verification.md#checks)). Distribution obligations live in [open-source policy](../docs/engineering/open-source.md#ffmpeg-distribution); the [workflows summary](../docs/engineering/workflows.md#ffmpeg-provisioning) routes here.

## Distribution

`dist` owns build/package/export/native/universal, smoke/install-smoke, library replacement, signing lifecycle, icons and nightly/draft publication. Its children import explicitly, and each platform's package tree sits beside that platform's audits in `distribution/{macos,linux,windows}.rs`; common tree assembly stays in `distribution/package.rs`. Its native media environment is shared with normal checks through `ffmpeg::environment_at`. [Packaging](../packaging/README.md) owns commands, inputs, limits, platform gates and recovery; [verification](../docs/engineering/verification.md) owns workspace checks. All generated output directories must be new. Credentials and sensitive platform tool output are suppressed, and safe command receipts stay local to outputs. Unit tests prove no oldest-OS, hardware or performance acceptance. The image crate regenerates PNG/ICO icons; normal builds consume committed icon assets.
